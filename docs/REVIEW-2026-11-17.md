## 1. What the system does today

1. A FastAPI backend (`satquery`) serves a React/MapLibre web app on one port, with demo accounts for farmer, field
   officer, district officer and state officer.
2. A rule-based risk engine scores 7 hand-drawn valley zones from three factors: pest-favourable weather
   (Open-Meteo), NDVI against earlier years (Sentinel-2 via Copernicus), and pest reports (currently **synthetic**).
3. LouNgak Watch derives alerts from each assessment: heavy rain (IMD categories), NDVI decline, and
   pest/disease-conducive weather.
4. Farmers report problems with a map pin. Officers triage a review queue, create and assign inspections, and field
   officers record outcomes that flow back to the farmer.
5. A statewide H3 map shows WorldCover farmland, a **SAMPLE** crop pattern and zone risk. A deterministic router
   answers English and Manipuri questions, and an optional Falcon VLM with a project-trained LoRA adapter answers
   image questions.

### What is already strong

- Clear honesty discipline in the backend: every input carries a status (SOURCED, SAMPLE, PLACEHOLDER, DEMO), and
  a missing factor is never estimated.
- Good test coverage, including a Python/TypeScript wire-contract test.
- Demo resilience features already exist: disk caches, a frozen snapshot fallback, an offline mode and a warm-up.
- Safe file handling: artifact paths are resolved under the runs directory (`server.py:396-401`), report HTML
  escapes user input, and upload names are sanitised.
- No credentials in any tracked file or in git history. `.env.example` has only placeholder values in every
  commit, and `.env`, `data/` and `runs/` are gitignored.
- The LoRA experiment is reproducible and honestly reported: a +16.6 point gain on a balanced held-out set, with
  its limits stated.

## 2. Critical problems, ranked

Severity scale. **P0** can break or discredit a live demo. **P1** is a security or permission bug. **P2** is a
correctness issue in the data or ML logic. **P3** is minor.

### P0: would break or discredit a live demo

**P0-1. A scheduled refresh freezes every page for the whole recompute.**
`AssessmentService.snapshot()` holds a lock while it recomputes (`satquery/agri/service.py:180-185`). After
`agri_refresh_s` (30 minutes), the next request recomputes all zones inside that lock. This covers weather for 7
zones, 4 NDVI windows per zone, and geocoding. Every endpoint that needs the snapshot waits: the overview, alerts,
the queue, and map cell clicks. On a slow venue network this means waits up to the provider timeouts, at an
unpredictable moment in the demo. The warm-up only covers the first computation.
*Fix:* serve the previous snapshot while a background thread recomputes (stale-while-revalidate). Block only when
no snapshot exists.

**P0-2. The zone ranking is largely decided by a hand-written SAMPLE config, and presentation mode hides it.**
`satquery/agri/assets/sample_scenario.json` sets `area_pressure` to `high` for Bishnupur and `elevated` for
Kakching and Thoubal. The generator gives Bishnupur 6 to 10 synthetic reports, which almost always saturate the
report factor at 1.0. The other zones get 0 to 2 low-severity reports.

With NDVI unavailable, which is common under monsoon cloud, two zones with the same weather index of 0.5 score:

| Zone | Calculation | Score | Level |
|---|---|---|---|
| Bishnupur | (0.5 × 0.5 + 0.2 × 1.0) / 0.7 | 0.64 | HIGH |
| Background zone | (0.5 × 0.5 + 0.2 × 0.1) / 0.7 | 0.39 | MODERATE |

The synthetic factor also counts as an "independent indicator" towards CRITICAL (`risk.py:152-156`).
Presentation mode is on by default. It rewrites "SAMPLE pest report" to "pest report" and the generator's name to
"LouNgak AI report feed" (`web/src/ui/presentation.ts`). Meanwhile, real farmer reports from the app are *not* fed
into the score.

A judge who asks where the report feed comes from, or why Bishnupur is always on top, exposes this. The user
decided on presentation mode for good reasons. The risk is that this one rewording reads as concealment, which
costs more credibility than the label would.
*Fix:* upgrade 1 below. Feed real app reports and inspection outcomes into the factor, and drop the SAMPLE source
or switch it off by default. Until then, keep the word "illustrative" on the report factor, even in presentation
mode.

**P0-3. Alerts change identity every day, which orphans tasks and acknowledgements overnight.**
The crop-health alert id ends with the NDVI window end, which is today (`satquery/watch/alerts.py:129-131`). The
pest/disease alert id ends with the first forecast day, which is also today (`alerts.py:154`). The next day the same
episode gets a new id, which causes three problems:

- an acknowledgement disappears, because `alert_state` is keyed by id;
- the alert returns to the review queue although a task exists, because `tasked_alerts` matches ids
  (`ops/service.py:164`);
- tasks raised from the alert drop off the map cell view, which links tasks to alerts by id (`agmap/__init__.py:339`).

This shows up in any demo that spans two days, or in a demo prepared the day before.
*Fix:* key an alert by rule, zone and episode start, where an episode continues while the rule keeps firing on
consecutive days. Alternatively, key it by rule and zone, and keep the dates as fields.

**P0-4. The DEMO alert never expires, and the validity it shows goes stale.**
`OpsService.alerts()` returns stored demo alerts without checking `valid_until` (`ops/service.py:68-79`). If
`seed-demo` was run before the state round, the DEMO heavy-rain alert now shows a validity date in the past.
Running `seed-demo` again refreshes the alert, but it also duplicates the two demo reports, because report ids are
sequential.
*Fix:* filter out expired alerts. Make `seed-demo` idempotent, or document `reset` followed by `seed-demo` as one
pre-demo step.

**P0-5. Copying `.env.example` as-is selects the real model, which is not installed by the default install.**
`.env.example` sets `SATQUERY_VLM_BACKEND=falcon`. The documented default install omits the `models` extra. Torch
is not installed in this repository's venv; the local `.env` sets `fake`, so this machine is fine. On a fresh demo
machine, the first open-ended image question tries to import torch and download about 3.4 GB. How the UI shows that
failure was not verified.
*Fix:* default `.env.example` to `fake`. Add a preflight check (step 3 in section 5) that refuses `falcon` when torch
is missing or the weights are not cached.

### P1: security and permissions

These matter as soon as the server is reachable from outside localhost, for example through a tunnel so judges can
use phones. The settings already anticipate this: `max_upload_mb` has a comment that "the server may be publicly
tunnelled".

**P1-1. Identity is a request header.** `optional_user` trusts `X-Demo-User` (`ops/users.py:38-45`), and
`/api/ops/users` lists every account id. Anyone can act as the state officer: dismiss reports, assign tasks, record
outcomes. This is documented as a demo limitation, but the README also says the server "enforces" role and
jurisdiction, which judges may read as access control.
*Fix (hackathon level):* a per-account demo PIN exchanged for a signed, HTTP-only session cookie. Bind to
127.0.0.1 unless a flag is set.

**P1-2. Creating a task bypasses jurisdiction and status checks.** `create_task` checks jurisdiction only for the
first report (`ops/service.py:220-231`). It then rewrites every listed report to UNDER_REVIEW with the new
`task_id` (`ops/service.py:240-244`), without checking each report's district or status. A Bishnupur district
officer can include a Thoubal report id and take it over. Any officer can also pull an INSPECTED or DISMISSED report
back to UNDER_REVIEW, and a report can sit in two tasks. Alerts in the same request are not checked against
jurisdiction either. This is a real bug even under the demo rules, because it breaks the stated permission model.
*Fix:* require `covers(user, r.district)` and `r.status in ("SUBMITTED", "UNDER_REVIEW")` with no open task, for
every report and alert. Add tests.

**P1-3. The report's district is free text, unchecked.** `ReportCreate.district` is any string (`ops/models.py:53`).
`create_report` does not check it against the farmer's own district or against the pin. A wrong or invented
district routes the report to the wrong officer, or to nobody but the state officer. The OpenStreetMap outlines
needed to derive the district from the pin already ship in the repository.
*Fix:* derive the district from the pin with the shipped outlines, and keep the farmer's choice only as a fallback
outside all outlines.

**P1-4. Unauthenticated uploads and spending of paid quota.** `/api/uploads` accepts up to 2 GB per file by default.
Files are never deleted, and the in-memory registry is lost on restart while the files stay on disk.
`/api/fetch-imagery` spends Copernicus processing units for any caller. There is no rate limit on either endpoint.
*Fix:* lower the default to about 200 MB, add a simple per-IP rate limit on the upload, fetch and analyze
endpoints, and clean the uploads folder on start-up.

### P2: correctness of the data and ML logic

**P2-1. Report ids can collide and silently overwrite a report.** `Store.next_id` reads the maximum id under the
lock, but `put` runs later under a separate acquisition (`store.py:35-38, 54-59`). Sync handlers run in a thread
pool, so two farmers submitting at once can get the same `RPT-000n`, and `INSERT OR REPLACE` drops one report. This
is unlikely with one presenter, but plausible if judges submit from their phones at the same moment.
*Fix:* allocate and insert in one locked transaction, or use an SQLite counter table.

**P2-2. The NDVI anomaly is too sensitive for harvest season, and its range check is unused.**

- A crop-health alert fires at a factor score of 0.3, which is a relative NDVI drop of about 8%
  (0.03 + 0.3 × 0.17).
- The NDVI covers all clear land in the zone, not cropland.
- `within_baseline_range` is computed but never used in the score (`risk.py:94-105`). A value inside the spread of
  the last three years still scores.
- In mid-November the valley paddy is being harvested. A harvest one or two weeks earlier than in earlier years
  gives an 8% drop easily, so false crop-health alerts are likely during the judging window.

*Fix:* score only when the current value falls outside the baseline range, or use a z-score against the
inter-annual spread. Mask NDVI to WorldCover cropland (upgrade 4).

**P2-3. The confidence label carries no information.** While any threshold is PLACEHOLDER, which is all of them,
every zone gets "low" confidence (`risk.py:176-178`). A label that never varies does not help an officer choose.
*Fix:* keep the PLACEHOLDER cap as a separate, visible flag. Let the label reflect data completeness and factor
agreement.

**P2-4. Pest and disease watches will likely fire almost everywhere.** `pest_watch` publishes a watch when a single
forecast day meets the rule (`alert_rules.json`: `min_favourable_forecast_days: 1`). The rice-blast rule needs 8
hours at 90% or more humidity and a mean of 20 to 28 °C, which is normal in the valley for much of the monsoon.
This was not measured against real data. It is a likely source of alert fatigue, and "everything is a watch"
weakens the triage story.
*Fix:* require 2 or more consecutive favourable days and a susceptible crop stage (see section 4). Log how often each
rule fires over a backfilled season.

**P2-5. One weather point per zone.** One weather point per zone is documented. It means valley zones a few
kilometres apart get near-identical weather factors, so their ranking is driven by the other factors. Together with
P0-2, that means the synthetic report factor.

**P2-6. The VLM is peripheral and trained out of domain.** The LoRA gain is real but narrow. It covers yes/no
questions on European BigEarthNet patches, and accuracy is 66% with a slight "yes" bias (1,015 yes against 779 no).
Present it as an engineering achievement in adaptation, not as agricultural evidence for Manipur.

### P3: minor

- `TaskCreate.due_on` and the outcome's GPS fields are not validated as a date or as coordinates
  (`ops/models.py:98-100, 117`).
- `/api/map/layers` rebuilds the GeoJSON of about 4,000 cells on every request. It is fine now, but cache it per
  snapshot.
- A review action of `under_review` on a report that is not SUBMITTED silently does nothing.
- The upload registry is in memory, so a server restart mid-demo turns the map's image layers into 404s.

## 3. Top 5 upgrades for the hackathon, ranked by impact against effort

| # | Upgrade | Impact | Effort |
|---|---|---|---|
| 1 | Close the loop: real reports and inspection outcomes drive the risk score | Very high | 1 to 1.5 days |
| 2 | Demo hardening: non-blocking refresh, stable alert ids, preflight | High (avoids failure) | 1 day |
| 3 | Permission fixes and automatic district routing from the pin | High | 0.5 to 1 day |
| 4 | Cropland-masked, range-aware NDVI, with per-cell scores on farmland | High | 1.5 to 2 days |
| 5 | One-click printable situation report per zone or district | Medium-high | 1 day |

### Upgrade 1: close the loop, with field truth driving the score

**Why judges care.** Today the strongest claim, "farmers and officers inform the system", is not true in the code.
The score uses synthetic reports, while real reports go elsewhere. Making farmer reports and verified inspection
outcomes drive `report_pressure` turns the product into a human-in-the-loop system and removes the largest
synthetic input (P0-2). It also gives a live demo moment: a farmer submits a report, and the zone's score and
reasons change on screen.

**Design.**

- Add a report source that reads the Store. Unverified farmer reports carry weight 1.0.
- A CONCERN_OBSERVED outcome carries 2.0.
- A CONCERN_NOT_OBSERVED outcome in the same zone and window subtracts, with a floor of 0.
- The factor's reasons cite report ids and their evidence status.
- The SAMPLE generator stays available behind a setting, off by default.
- Creating a report or recording an outcome invalidates the cached snapshot.

**Files.** `satquery/agri/reports.py` (new `FieldReportSource`), `satquery/agri/pipeline.py` (`default_sources`,
`Sources`), `satquery/agri/service.py` (accept the Store and expose `invalidate()`), `satquery/agri/risk.py`
(`report_factor` wording and outcome weighting), `satquery/agri/assets/risk_model.json` (outcome weights, still
PLACEHOLDER), `satquery/ops/service.py` (call `invalidate()`), `satquery/server.py` (wiring),
`web/src/ui/presentation.ts` (remove the rewording that hid SAMPLE), tests.

### Upgrade 2: demo hardening

**Why judges care.** A frozen page or a stale "valid until" date in front of judges costs more than any feature
gains. This closes P0-1, P0-3, P0-4 and P0-5.

**Scope.**

- A non-blocking refresh.
- Alert ids keyed by episode.
- Expired alerts filtered out.
- An idempotent `seed-demo`.
- `.env.example` defaulting to `fake`.
- A preflight command that checks `web/dist`, the VLM backend against the installed packages, Copernicus
  credentials, snapshot age, seed state and database writability, then prints PASS or FAIL.

**Files.** `satquery/agri/service.py`, `satquery/watch/alerts.py`, `satquery/ops/service.py`, `satquery/ops/seed.py`,
`satquery/ops/__main__.py`, `.env.example`, `README.md` (pre-demo routine), tests.

### Upgrade 3: permission fixes and automatic district routing

**Why judges care.** "Reports reach the right officer automatically" is a concrete governance claim, and the
outlines needed for it already ship. The permission fixes protect the claim that the server enforces jurisdiction.

**Scope.** P1-2, P1-3 and P2-1. Add a point-in-district lookup on
`satquery/agri/assets/manipur_districts_osm.geojson`, with the stated district as a fallback, and record which of the
two was used.

**Files.** `satquery/agri/districts.py` (new `district_for(lat, lon)`), `satquery/grid.py`, `satquery/ops/service.py`
(`create_report`, `create_task`), `satquery/ops/models.py` (`district_source` field), `satquery/store.py`
(`next_id`), `web/src/state/types.ts`, `tests/test_contract.py`, `web/src/pages/ReportPage.tsx` (show the detected
district), tests.

### Upgrade 4: cropland-masked, range-aware NDVI with per-cell scores on farmland

**Why judges care.** It removes two caveats judges will spot: "NDVI over all land" and "cells only show their
zone's level". The map then shows which farmland cells inside a zone are below their own past, which is a GIS
result rather than a coloured rectangle.

**Design.**

- Compute the NDVI windows per farmland cell. Use H3 resolution-7 cells inside monitored zones with a WorldCover
  cropland share of 30% or more, through the existing Statistical API path.
- Past windows are cached forever, so the cost is one current window per cell per day.
- Score a cell only when it falls outside its baseline range (P2-2).
- The zone factor becomes the share of its farmland cells in decline.

Check the Copernicus processing-unit cost on one zone before running all of them.

**Files.** `satquery/agri/ndvi.py`, `satquery/agri/risk.py` (`ndvi_factor`), `satquery/agri/assets/risk_model.json`,
`satquery/agmap/__init__.py` (cell properties and `cell_detail`), `web/src/agmap/AgLayers.tsx`, `CellPanel.tsx`,
`LayerPanel.tsx`, `web/src/state/types.ts`, `tests/test_contract.py`, tests.

### Upgrade 5: printable situation report

**Why judges care.** Officers work on paper and WhatsApp. A one-page report per zone or district is something a
judge can hold, and it shows the explainability work: level, factor points, evidence, limitations, open reports,
inspections and outcomes, sources and timestamps. This is already first on the Stage 2 list in `Context/progress.md`.

**Files.** New `satquery/reports/situation.py` (an HTML template using the existing escaping approach), a route in
`satquery/agri/routes.py` (`GET /api/agri/areas/{id}/report`), a button in `web/src/agri/AreaRiskDrawer.tsx` and
`web/src/agmap/CellPanel.tsx`, and print CSS.

## 4. One idea that would make it stand out: cloud-proof paddy monitoring from Sentinel-1 radar

**The problem it solves.** In the monsoon, when blast and planthopper risk is highest, cloud hides the Manipur valley
and the NDVI factor is unavailable. The README says so. The crop-type layer is also SAMPLE. These are the two
biggest gaps in the product, and both come from relying on optical imagery.

**The idea.** Build a per-cell rice calendar from the Sentinel-1 VH backscatter time series, which sees through
cloud. Use one value per farmland cell per acquisition, every 6 to 12 days depending on the satellites in orbit.
Transplanted paddy has a well-documented radar signature: a sharp VH drop when fields are flooded, then a steady rise
as the canopy grows, then a fall at harvest. From each cell's series:

1. **Where rice actually is this season.** Cells with the flooding-then-growth signature are rice, which replaces
   the SAMPLE crop layer for rice with an observed map.
2. **When it was transplanted.** This gives the crop stage per cell, so the pest rules become stage-aware. For
   example, neck blast only matters around heading. This directly cuts the alert fatigue in P2-4.
3. **An all-weather anomaly.** Compare growth against the cell's own previous seasons. The comparison still works
   when NDVI cannot be measured.

**Why it is a real edge and not just a feature.** It is a method with a measurable result.

- Validate the rice map against district rice-area statistics, for example from the Directorate of Economics and
  Statistics.
- Validate the transplanting dates against farmer reports and inspection records, which upgrade 1 starts to
  collect.
- Report the agreement honestly.

"A validated, cell-level, all-weather rice calendar for the Manipur valley, built from free Sentinel-1 data" is a
research claim judges and recruiters can check. The building blocks exist: Sentinel-1 retrieval and the Copernicus
Statistical API are already in `satquery/providers/copernicus.py` and `satquery/agri/ndvi.py`.

**Limits to state up front.**

- Valley paddy only. Hill jhum is not covered, because terrain and mixed cropping break the signature.
- Speckle needs temporal smoothing.
- The thresholds need tuning on a few known fields.

**Effort.** 3 to 5 days. Treat it as the national-round headline, after upgrades 1 to 3.

## 5. Implementation plan for a follow-on model

### Ground rules for every step

- Work on a new branch from `feat/agri-map`, for example `feat/stage2-hardening`. Commit after each step, with the
  step number in the message.
- Keep the honesty conventions:
  - never relabel PLACEHOLDER as VERIFIED, or SAMPLE as real;
  - never estimate a missing input;
  - every new data source carries a `Provenance` with a state.
- Every new or changed wire model needs its TypeScript mirror in `web/src/state/types.ts` and an entry in
  `tests/test_contract.py`.
- If server wording changes, check the patterns in `web/src/ui/presentation.ts` still match, or remove them.
- After each step, all of the following must pass:
  - `.venv\Scripts\python -m pytest`
  - `npm test`, `npm run typecheck` and `npm run build` in `web/`
- Do not touch `experiments/`, `adapters/` or the live/GPU tests.

### Step 0: baseline

- Run the full test suites and record the counts. The backend count on 17 Nov 2026 was 852 passed and 3 skipped.
- **Acceptance:** both suites green before any change.

### Step 1: permission and integrity fixes (P1-2, P2-1, P3 validation)

- In `create_task`, check every report and every alert for jurisdiction, open status and the absence of another
  open task.
- Make `Store.next_id` allocate and insert atomically: add `Store.insert_new(kind, prefix, build)`, or a counter
  table.
- Validate `due_on` as an ISO date, and the GPS fields as coordinates.
- **Acceptance:**
  - New tests show that a Bishnupur officer bundling a Thoubal report gets 403.
  - Re-tasking an INSPECTED report gets 409.
  - 50 concurrent `create_report` calls in threads produce 50 distinct ids and 50 rows.
  - All existing tests pass.

### Step 2: non-blocking assessment refresh (P0-1)

- In `AssessmentService.snapshot()`, return the existing snapshot immediately when it is older than the refresh
  period, and start at most one background recompute.
- Block only when no snapshot exists.
- Add `invalidate()`, which marks the snapshot stale without discarding it.
- **Acceptance:**
  - A test with a source that sleeps 2 s shows that a call after expiry returns the old snapshot in under 100 ms.
  - A later call returns the new one.
  - Only one recompute runs under 10 concurrent calls.

### Step 3: alert identity, expiry, seed and preflight (P0-3, P0-4, P0-5)

- Key alerts by rule, zone and episode. An episode starts on the first day of a run of consecutive firing days,
  computed from the evaluated days already in `PestEvaluation.days` and the NDVI window history.
- Filter out alerts whose `valid_until` has passed, including demo alerts.
- Make `seed-demo` idempotent, with fixed ids for the demo records, and have it refresh their dates.
- Set `SATQUERY_VLM_BACKEND=fake` in `.env.example`.
- Add `python -m satquery.ops preflight`. It checks `web/dist`, the VLM backend against importable torch,
  Copernicus credentials, snapshot age under 24 h, database writability and the seed state, and exits non-zero on
  any FAIL.
- **Acceptance:**
  - A test that derives alerts on two consecutive days with the same firing rule gets the same id.
  - An acknowledgement and `tasked_alerts` survive the day change.
  - An expired demo alert is not listed.
  - Running `seed-demo` twice leaves exactly 2 demo reports and 1 demo alert.
  - Preflight fails on a machine with `falcon` and no torch.

### Step 4: automatic district routing (P1-3)

- Add `districts.district_for(lat, lon)` using the shipped OSM outlines, cached once at load.
- In `create_report`, use it, and store `district_source` as `"outline"` or `"reporter"`.
- If the farmer's account districts do not include the result, accept the report but add a history note.
- Show the detected district on `ReportPage.tsx` once the pin is set.
- **Acceptance:**
  - A pin inside Thoubal with the stated district "Bishnupur" is stored as Thoubal, with `district_source`
    `"outline"`.
  - A pin outside all outlines keeps the stated district, with `"reporter"`.
  - The contract test passes.

### Step 5: field reports drive the score (upgrade 1, P0-2)

- Add `FieldReportSource(store)`, with the same `for_area()` signature as `SampleReportSource`. It returns real
  reports in the zone and lookback window, with outcome adjustments as designed in section 3.
- Add `SATQUERY_AGRI_REPORTS=field|sample`, defaulting to `field`.
- Pass the Store into `AssessmentService` from `create_app`, and call `invalidate()` after report creation and
  outcome recording.
- Update the factor name and reasons. Delete the `presentation.ts` rewording of the SAMPLE report source.
- **Acceptance:**
  - With an empty database, the report factor is 0 with the reason "no field reports in the last 14 days".
  - It is not unavailable, and is not SAMPLE.
  - After one farmer report in a zone, the next overview shows that zone's report points above 0 and cites the
    report id.
  - A CONCERN_NOT_OBSERVED outcome lowers it.
  - `includes_sample_data` is false when the source is `field`.

### Step 6: range-aware, cropland-masked NDVI (upgrade 4, P2-2)

- **6a, cheap.** In `ndvi_factor`, score 0 when `within_baseline_range` is true, and say so in the reasons.
- **6b.** Per farmland cell inside a zone, meaning H3 resolution 7 with a cropland share of 0.3 or more, compute the
  NDVI anomaly through the existing `NdviClient.window()` with the cell polygon. Cache it as today.
- The zone factor is the share of its farmland cells outside their range on the low side, scaled by the existing
  breakpoints.
- Expose `ndvi_change` per cell in `/api/map/layers` and in `cell_detail`, and add a map layer.
- Measure the processing units for one zone first, and stop if a full run exceeds the free quota.
- **Acceptance:**
